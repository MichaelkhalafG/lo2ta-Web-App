## Decisions

Each decision: what, why, the alternative rejected and why, and what reversing it would cost.

### D1. The activity log screen is admin only (gate `view-activity`)
- **Decision:** only the admin role sees and opens `/dashboard/activity`; the reviewer gets a 403 page.
- **Why:** PLAN 2.4 lists what the reviewer does (units, documents, requests, deals); the log holds every write by
  every person, including settings and staff changes, which are admin matters.
- **Rejected:** open to both roles. Cheap, but shows the reviewer admin-only actions and their before/after values.
- **Reversing:** one line in `AppServiceProvider` (drop `view-activity` from the admin-only list) and one test.

### D2. CSV export is admin only (gate `export-data`)
- **Decision:** the copied table export works only for the admin role.
- **Why:** exports move data out of the platform; the plan gives data-heavy screens (commissions, staff) to the admin.
- **Rejected:** export for both roles, for the same reason as D1.
- **Reversing:** one line in `AppServiceProvider`.

### D3. One dashboard Error page instead of separate Error and NotFound pages
- **Decision:** `Pages/Error.tsx` renders 403, 404, 419, 500 and 503 in both languages; the copied NotFound page was
  removed. 500/503 keep Laravel's debug page while `APP_DEBUG` is on.
- **Why:** one screen, one set of strings, the same look for every failure.
- **Rejected:** keeping both copied pages: two places to translate and dress for the same job.
- **Reversing:** add a page component and a branch in `bootstrap/app.php`.

### D4. Checked and selected states in the dashboard use text-1, never gold
- **Decision:** checkboxes, switches and selected rows use the light text colour (text-1) on the dark ground; gold stays
  for the one primary button of a screen (shadcn `primary`).
- **Why:** the board limits gold to under 2% of a screen and to the primary action; a table of checked rows would
  turn gold everywhere.
- **Rejected:** gold for checked states (breaks the 2% rule) or the verified cyan (would read as "verified").
- **Reversing:** change the class map in four ui components.

### D5. The dashboard header is 64px, the public header 80px
- **Decision:** `--spacing-header` is 4rem in the dashboard; the public site keeps the token's 80px.
- **Why:** the token describes the public site; staff screens are dense work screens with a sidebar.
- **Rejected:** 80px in the dashboard: 16px less table on every screen for no gain.
- **Reversing:** one value in `core/resources/css/app.css`.

### D6. The dashboard copies the paper colours it does not use
- **Decision:** `core/resources/css/lokta-tokens.css` carries every reference colour, paper band included.
- **Why:** the token check then compares the full set, so a later use of a paper colour cannot drift silently.
- **Rejected:** copying only the colours in use (the check would have to know which ones are skipped).
- **Reversing:** delete five lines and teach the check an exclusion list.

### D7. The hero override is a named token
- **Decision:** Michael's answer (86px hero) is the token `text-hero` in `web/src/styles/lokta-theme.css`, used as
  `lg:text-hero`; `display-xl` keeps the design file's 96px.
- **Why:** a named override shows up in the theme next to the value it overrides, not as an arbitrary class.
- **Rejected:** an arbitrary `lg:text-[5.375rem]` class (the previous state).
- **Reversing:** one line in the theme and one class.

### D8. The copied DataTable gets a multi-filter setter
- **Decision:** a third slot argument `setFilters(values)` sends several filters in one visit.
- **Why:** a date range set with two `setFilter` calls started two visits; the second overwrote the first and the
  start date was lost (found while porting the activity screen).
- **Rejected:** chaining visits (two requests, flicker) or a date-range special case inside the table.
- **Reversing:** remove the argument; nothing else depends on it yet except the activity screen.

### D9. Phase commit scripts stage a snapshot, not the working tree
- **Decision:** at the end of each phase its files are copied to `D:\coding\lokta-pause-2026-11-17\phaseN\snapshot\`
  with a sha256 manifest; `commit-phaseN.ps1` stages those snapshot contents into git's index (`git hash-object -w`
  and `git update-index --cacheinfo`) and commits. The working tree is not touched.
- **Why:** both scripts are run after the whole run, and phase 3 edits files phase 2 also changed (PLAN, routes, lang
  files). `git add` would put phase 3 work into the phase 2 commit. The snapshot is exactly the phase's state, and it is
  also the required copy of uncommitted work outside the repository.
- **Rejected:** `git add` of the phase's file list (mixes phases); one combined commit (Michael asked for one per phase);
  patch files applied with `git apply --cached` (fails on the new binary font files without extra flags).
- **Reversing:** `git reset --soft HEAD~1` after either script; the working tree is unchanged by the scripts.

### D10. Public sign-in: core issues a token, the Next server keeps it in an httpOnly cookie
- **Decision:** accounts live in core; `POST /api/v1/auth/login|register` return a Sanctum token; the Next server
  stores it in the `lk_session` cookie (httpOnly, Secure in production, SameSite Lax, 30 days) and sends it to core
  as `Authorization: Bearer` with the server key. Tokens only: no Sanctum cookie mode, no fallback to the web guard.
- **Why:** core keeps every rule and write (handover 2.1); the browser never holds the token or the server key; works
  with the static, cached public pages.
- **Rejected:** account pages served by core (a second site look and domain); a browser-side token in local storage
  (readable by any script on the page); a custom token table (Sanctum is the standard, tested piece).
- **Reversing:** the token layer sits in `lib/session.ts`, `lib/account.ts` and `config/sanctum.php`; replacing it
  touches those files and the `auth:sanctum` route group.

### D11. Rate limits use the visitor IP forwarded by the Next server
- **Decision:** the Next server sends `X-Client-Ip` (from `x-forwarded-for`); core uses it for rate limits only on
  requests that passed the server key. Limits: sign-in 5 a minute per e-mail and IP, registration 5 an hour per IP,
  reset requests 10 an hour per IP, resend 1 a minute per account, link checks 20 a minute per IP.
- **Why:** every account call reaches core from the web server's IP; without the header one visitor's mistakes
  would block everyone.
- **Rejected:** limits by the request IP (blocks the whole site at once); no limits (Q18 asks for them).
- **Reversing:** `App\Support\Accounts\ClientIp` and the numbers in the auth controller.

### D12. Budget unit types are a JSON list on the budget, not a pivot table
- **Decision:** `buyer_budgets.main_types` holds the chosen main type codes; areas and compounds keep pivot tables.
- **Why:** the four main types are fixed codes (an enum), not rows; a pivot adds a table for no query gain.
- **Rejected:** `buyer_budget_types` pivot as first sketched in PLAN 3.6.
- **Reversing:** a migration that moves the list into a pivot; matching (phase 7) is not written yet.

### D13. My account edits the name, mobile and e-mail language; the e-mail itself is not editable
- **Decision:** `PUT /api/v1/me` changes name, mobile (Egyptian format) and the language of e-mails, logged.
- **Why:** staff call people (Q11), so a typo in the mobile must be fixable; the e-mail is the sign-in identity and
  changing it needs its own verification flow, which the plan does not list.
- **Rejected:** no editing (a wrong mobile could never be fixed); e-mail change (a second verification flow).
- **Reversing:** drop the route and the form section.

### D14. The "new budget" e-mail goes to every active admin account
- **Decision:** until the client names a team mailbox, `admin.new_budget` goes to each active admin user.
- **Why:** PLAN 2.3 asks for an e-mail to "the admin team" and no team address is known (PLAN 6 row 15, a fact we must
  not invent).
- **Rejected:** a made-up address; no e-mail.
- **Reversing:** a `team_email` setting and one line in `BudgetController`.
- **Answered 2026-11-18:** team notices go to one of the agreement's two official mailboxes (e.g. info@loktaeg.com),
  held in the setting `team_email`; while it is empty, every active admin still gets them.

### D15. Saving a budget does not need a confirmed e-mail
- **Decision:** a signed-in buyer can save a budget before confirming the e-mail; the team e-mail shows whether the
  e-mail is confirmed.
- **Why:** Q13 requires a confirmed e-mail to submit a unit or a request; the budget is neither, and asking for it later
  stays possible.
- **Rejected:** blocking the budget until confirmation (one more step before the buyer gives us anything).
- **Reversing:** one check in `BudgetController` and a message on the page.

### D16. The public header stays the same for everyone
- **Decision:** the header keeps "دخول / Sign in"; a signed-in visitor who opens /login goes straight to My account.
- **Why:** reading the session in the header would make every public page per-visitor and end ISR caching
  (handover 2.2); the account pages are one click away.
- **Rejected:** a per-visitor header (every page dynamic).
- **Reversing:** a small client component that asks `/api/me` after load (adds a request per page view).

### D17. Link lifetimes: e-mail confirmation 24 hours, password reset 60 minutes
- **Decision:** the confirmation link is signed (HMAC over id, e-mail hash and expiry) and lasts 24 hours; the reset
  link uses Laravel's broker (60 minutes, one request a minute).
- **Why:** people open confirmation e-mails later; a reset link should be short-lived.
- **Rejected:** Laravel's 60-minute confirmation default.
- **Reversing:** `Links::VERIFY_HOURS` and `config/auth.php`.

### D18. A password reset signs the account out everywhere
- **Decision:** a successful reset deletes every token of the account.
- **Why:** a reset is often done because someone else knew the password.
- **Rejected:** keeping other sessions.
- **Reversing:** one line in the reset callback.

### D19. Favorites: only public units can be saved; a saved unit that leaves keeps its code only
- **Decision:** `POST /me/favorites` accepts published or reserved units; "My favorites" shows a unit that left the
  market with its code and "no longer available", nothing else.
- **Why:** PLAN 2.3 ("marking units no longer available") and 2.5 (nothing private, nothing of a withdrawn listing).
- **Rejected:** hiding departed favorites (the buyer would wonder where they went).
- **Reversing:** the mapping in `FavoritesController::index`.

### D20. Optional e-mails left out: no welcome e-mail, no "budget saved" e-mail to the buyer
- **Decision:** the buyer gets the confirmation e-mail and reset e-mails only; the page confirms a saved budget.
- **Why:** PLAN 2.1 and 2.3 mark both as optional; fewer e-mails means fewer texts for the client to write.
- **Rejected:** sending both.
- **Reversing:** two templates and two outbox calls.
